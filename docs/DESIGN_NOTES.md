# 设计说明：创新点 · 优缺点 · 大促动机

配套工程：本框架用三个独立 node 进程模拟三个数据库节点（user:6001 / shop:6002 / txn:6003），
数据库以 JSON 文件落盘，`python run_all.py` 一键拉起并跑 7 个案例。

---

## 一、创新点（区别于 2PC/XA、TCC、本地消息表、最大努力通知）

1. **脑裂是从结构上被删除的，不是靠算法防的。**
   每个库只保证单库本地事务 + 单库高可用（MGR/Raft 只在单库内部）；**库与库之间不通信、不投票、不感知**。
   既然不存在库间共识通道，就不存在"多库同时作主"的脑裂——故障类别被结构性消除。

2. **跨库锁变成可超时、可观察、可补偿的本地冻结标记。**
   冻结只是本地事务里打标记，真实余额/库存数字不变；带 TTL，超时可判定事务已死；可枚举、可对账。

3. **双层自愈，第二层是独创（节点启动自检自治回滚）。**
   - 第一层：协调器轮询器 + 死信，重连核对、指数退避。
   - 第二层：节点宕机/隔离重启后，**主动回查全局事务中心要未完成事务，核对本地冻结标记，在本地事务内自动补偿**，再回写全局状态。
   补上了常规 SAGA/TCC 的死区：协调器连不上下游时，补偿不再永久悬挂。

4. **按操作相位精确补偿，不会补错方向。**
   相位 `PENDING → FROZEN → COMMITTED → COMPENSATED`：已扣真实值的才返还，只冻结的只解冻。

5. **唯一残余风险做成闭环兜底。**
   全局事务状态库多副本 + 快照备份；离线对账交叉校验流水/单据，检出孤儿冻结自动解冻并告警。

6. **业务零侵入。** 对外就是 `gateway.order(...)` 虚拟原子调用；全局事务 ID + 幂等号保证重试/重放不重复扣减。

---

## 二、优点

- 从结构上消除多库脑裂。
- 无跨库长事务，库侧都是本地短事务，并发吞吐高。
- 双层自愈消除 SAGA/TCC 悬挂死区。
- 幂等 + 相位补偿，重试安全。
- 业务零感知，跨库细节全被框架吃掉。

## 三、缺点与局限（诚实清单）

1. **是最终一致，不是强一致。** 冻结到 SUCCESS 之间有中间态；银行核心记账级强一致不适用。
2. **TXN 全局事务状态库成了新的关键中心。** 它是所有事务必经写入点，长时间不可用则框架无法新建/推进事务；这把"库间脑裂"风险转移成了"协调者/状态库可用性与吞吐"问题。
3. **延迟与写放大约翻倍。** 任何跨主体操作都要"冻结 + 提交"两段，且每段写状态库。
4. **冻结占用额度的 TTL 需要精调。** 太短误杀正常重试，太长额度被无效占用。
5. **离线对账是兜底不是实时。** 孤儿冻结检出有延迟，期间额度被错误占住。
6. **生产化还要补。** 演示里轮询器是单进程；真实部署要轮询器选主、分布式死信队列、自检与轮询的并发竞争控制。
7. **扩展性靠纪律。** 新资产操作必须正确实现 freeze/commit/compensate 三接口且幂等，编译器不强制。
8. **调试成本高。** 一笔问题事务要跨协调器 + 三个节点日志来回对。

### 适用边界

| 适合 | 不适合 |
|---|---|
| 高并发跨业务主体、可接受秒级最终一致 | 需要毫秒级强一致（银行核心记账） |
| 订单-库存-余额这类"扣完能退"的资产操作 | 中间态暴露即重大事故的场景 |
| 多独立库、不想扛跨库一致性投票 | 单库事务就能解决的问题（属过度设计） |

---

## 四、为什么大促要这样做

大促（秒杀/双十一级）的三个死结：**高并发写、零超卖超花、故障是常态**。

1. **不能被跨库长事务锁死。** 秒杀瞬间若用 XA，库存行/用户余额行会被跨库长事务长时间持锁，QPS 一上来锁等待雪崩、连接池打满。预冻结只打标记、毫秒释放行锁——这是扛洪峰的根本。
2. **先接住流量，再异步清账。** 冻结成功 ≈ 下单成功，立刻返回用户"已锁定"；真实扣减、清账放后面分步完成。同步路径极短，重活全异步。
3. **绝不超卖超花。** 可用值 = 真实值 − 已冻结，这个校验在单库本地事务内做，不依赖远端，洪峰下不会重复卖同一批货、重复扣同一笔钱。
4. **大促当晚一定有节点挂。** 双层自愈让"挂了也能自己回来"，不需要半夜人工对单；死信退避 + 节点重启自检把补偿闭环。
5. **不搞跨库投票。** 网络抖动时跨库 Raft/MGR 可能脑裂双写 = 资损事故。让每个库只做单库高可用，跨库一致性交给无状态、可水平扩、重启就好的业务层。
6. **幂等是刚需。** 超时重试、消息重投、用户狂点"支付"是常态，全局事务 ID + 幂等号保证不重复扣款/扣库存。
7. **离线对账是大促后的安全网。** 凌晨自动找孤儿冻结、不平的账并告警，人工第二天只处理 `MANUAL_REVIEW` 那一撮。

> 一句话：大促要的不是"最严格的跨库一致"，而是"洪峰下不锁死、并发下不超卖超花、挂了能自己回来、最后还能对平账"。本架构按这个优先级，用最终一致换掉跨库投票，换来锁粒度与无脑裂可用性——代价（中间态、TXN 中心、对账成本）在大促里是可接受的工程取舍。
